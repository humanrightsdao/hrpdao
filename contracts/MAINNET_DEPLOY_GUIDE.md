# Покрокова інструкція mainnet-деплою (Arbitrum One)

Побудована на основі реального тестового прогону на Arbitrum Sepolia
(усі 16 контрактів задеплоєно успішно, 76/76 тестів, реальний газ
`verifyProof()` виміряно). Тут враховані нюанси й збої, знайдені саме
під час тестового прогону — це не абстрактний чек-лист, а інструкція,
що вже "наступила на граблі" один раз.

## ⚠️ Найважливіша відмінність від тестового прогону

Під час Sepolia-репетиції ми виявили: команда `--resume` у вашій
версії `forge` (1.5.1) **не пропускає** вже задеплоєні контракти, а
**перезапускає весь скрипт заново**. `Deploy.s.sol` НЕ ідемпотентний —
кожен `new X(...)` створює контракт за НОВОЮ адресою. На тестнеті це
коштувало лише зайвого тестового ETH. **На mainnet повторний
неконтрольований запуск означає реальні подвійні витрати й, гірше,
двоплутану систему з дублікатами контрактів.**

Тому інструкція нижче будує деплой так, щоб звести ймовірність
переривання до мінімуму, і дає чіткий протокол дій, якщо переривання
все ж станеться — БЕЗ автоматичного `--resume`.

## Частина 0 — Фінальна звірка перед стартом (окремо від самого деплою)

**Не переходьте до Частини 1, доки кожен пункт нижче не позначено ✅.**

1. Пройти повністю `MAINNET_PARAMETERS_CHECKLIST.md` — кожен параметр
   команда підтвердила свідомо, особливо три ⚠️-пункти (inactivity
   window, реальний verifier, IPFS-плейсхолдери).
2. `src/HexAncestryVerifier.sol` — перевірити, що це файл, згенерований
   з РЕАЛЬНОГО публічного ptau (не тестового). Швидка перевірка: файл
   не повинен містити коментар "ЛОКАЛЬНОГО ТЕСТОВОГО ptau" з
   попередньої версії — якщо він там є, ви дивитесь не в той файл.
3. `.env` — `TESTNET=false` встановлено явно.
4. Обидва Safe-мультисиги (`GUARDIAN_MULTISIG`, `EPOCH_SUBMITTER`)
   реально задеплоєні на Arbitrum One (не лише "counterfactual"-адреси
   без коду) — **АБО** ви свідомо покладаєтесь на "ліниве розгортання
   при першій транзакції" Safe (це працює, але перевірте перед стартом
   через `cast code <адреса> --rpc-url $ARBITRUM_ONE_RPC_URL` — якщо
   виводить `0x`, код ще не розгорнутий; це не блокер для
   `Deploy.s.sol`, бо там лише `grantRole` на адресу, без виклику коду,
   але майте на увазі, що GUARDIAN/EPOCH_SUBMITTER не зможуть НІЧОГО
   зробити, доки Safe не активується їхньою першою транзакцією).
5. Звірити **посимвольно** обидві адреси мультисигів у `.env` з тим,
   що показує сам Safe UI — одна помилка символу тут означає втрату
   контролю над роллю назавжди (це `immutable`-подібне рішення на
   практиці, бо переприв'язати роль можна лише новою DAO-пропозицією,
   а на генезисі ще нема кому голосувати).
6. Реальні адреси USDC/USDT/DAI/PASSPORT_DECODER (розділ 14
   `MAINNET_PARAMETERS_CHECKLIST.md`) — звірені на arbiscan.io
   особисто, не лише скопійовані з документа.
7. Гаманець-деплоєр має достатньо **реального** ETH на Arbitrum One.
   Орієнтир з тестового прогону: ~28M газу сумарно. Порахувати
   актуальну вартість: `28_000_000 × поточна_ціна_газу_gwei / 1e9` ETH.
   Перевірити поточну ціну газу на https://arbiscan.io/gastracker.
   Додати запас **мінімум 30%** зверху (mainnet-умови можуть
   відрізнятись від Sepolia).
8. `PRIVATE_KEY` у `.env` — це гаманець-деплоєр, **окремий** від обох
   мультисигів, з достатнім балансом (п.7), і це НЕ гаманець, яким ви
   користуєтесь для чогось іншого одночасно (щоб уникнути race
   condition по nonce).

## Частина 1 — Підготовка сесії (той самий крок, що на Sepolia)

1. `cd` у корінь проєкту в Git Bash.
2. `source .env` — обов'язково, інакше `$VAR`-підстановки в
   командах нижче будуть порожніми (це саме та помилка, що траплялась
   на Sepolia).
3. Перевірити, що підставилось:
   ```
   echo $PRIVATE_KEY | cut -c1-6
   echo $GUARDIAN_MULTISIG
   echo $EPOCH_SUBMITTER
   echo $TESTNET
   ```
   (`PRIVATE_KEY` виводимо лише перші 6 символів — навіть цього
   достатньо, щоб пересвідчитись, що змінна не порожня, не
   світячи повний ключ у терміналі).
4. Додати в `.env` (або передати змінною середовища) надійний RPC для
   Arbitrum One — **не публічний безкоштовний RPC** для такого
   критичного одноразового деплою, а платний ендпоінт (Alchemy/Infura/
   QuickNode) з вищою надійністю й лімітами:
   ```
   ARBITRUM_ONE_RPC_URL=<ваш платний RPC-ендпоінт>
   ```

## Частина 2 — Сухий прогін (симуляція, БЕЗ витрати реального газу)

**Це найважливіший новий крок порівняно з тим, як ми йшли на Sepolia**
— там ми одразу зробили `--broadcast`. На mainnet спершу симулюємо.

```
source .env
forge script script/Deploy.s.sol:Deploy --rpc-url $ARBITRUM_ONE_RPC_URL --chain arbitrum-one -vvvv
```

Без `--broadcast` — жодна транзакція не йде в мережу, лише повна
симуляція на форку поточного стану ланцюга.

**Перевірте у виводі:**
- `Script ran successfully` — без жодного revert
- Блок `Simulated On-chain Traces` — усі очікувані 16 контрактів
  з'являються, з правильними значеннями параметрів (звірте пару
  ключових — `MinDelayChange: newDuration: 259200` = 72 години в
  секундах, `VotingDelaySet`/`VotingPeriodSet` тощо)
- Рядок `Estimated total gas used for script` і `Estimated amount
  required` — це РЕАЛЬНА оцінка на поточному стані mainnet, звірте з
  балансом гаманця-деплоєра (Частина 0, п.7)

**Якщо тут щось не так — зупиняйтесь.** Виправляти `.env`/код і
переробляти симуляцію набагато дешевше, ніж виправляти вже
задеплоєний mainnet-контракт.

## Частина 3 — Реальний деплой

Коли симуляція пройшла чисто:

```
forge script script/Deploy.s.sol:Deploy --rpc-url $ARBITRUM_ONE_RPC_URL --chain arbitrum-one --broadcast --verify --etherscan-api-key $ETHERSCAN_API_KEY --slow -vvvv
```

Відмінності від команди, яку ми використовували на Sepolia:

- **`--verify` одразу в цій же команді**, а не окремим `--resume`-
  проходом пізніше — саме тому, що ми з'ясували ненадійність
  `--resume` у цій версії forge. Якщо верифікація частково не
  спрацює — це виправляється окремо, безпечно, через
  `forge verify-contract` для кожного контракту індивідуально
  (`verify-contract` ніколи нічого не бродкастить, лише читає
  вже задеплоєний байткод).
- **`--slow`** — форс чекає підтвердження (receipt) кожної
  транзакції, перш ніж відправити наступну. Повільніше, але прибирає
  ризик nonce-плутанини при мережевих затримках — для одноразового
  критичного mainnet-деплою це варте того.

**Під час виконання:**
- Не закривайте термінал, не переривайте Ctrl+C "про всяк випадок" —
  саме так стався небажаний повторний прогін на Sepolia. Дайте
  команді завершитись природно.
- Якщо з'явиться `[Pending]` надовго (мережева затримка) — це
  нормально при `--slow`, просто чекайте.

## Частина 4 — Якщо деплой перервався посередині

**НЕ виконуйте `--resume` автоматично.** Натомість:

1. Відкрийте `broadcast/Deploy.s.sol/42161/run-latest.json` —
   подивіться, скільки транзакцій там зафіксовано як `"status": "0x1"`
   (успішні) і на якому контракті зупинилось.
2. Перевірте безпосередньо в мережі, чи контракт з останнього
   успішного кроку справді має код:
   ```
   cast code <адреса_останнього_контракту> --rpc-url $ARBITRUM_ONE_RPC_URL
   ```
   Якщо виводить щось довше за `0x` — контракт реально задеплоєний.
3. **Зверніться до розробника/мене з цим логом** перш ніж вирішувати,
   що робити далі — правильний шлях (написати кастомний
   продовжувальний скрипт, що підхоплює вже задеплоєні адреси й
   виконує лише решту кроків) залежить від того, на якому саме кроці
   стався збій. Це не має вирішуватись наосліп повторним запуском
   усього `Deploy.s.sol`.

## Частина 5 — Одразу після успішного деплою

1. Скопіюйте адреси всіх 16 контрактів з виводу (`=== HR DAO deployed
   ===`) у постійне місце (не лише в термінал, який можна закрити) —
   наприклад, `MAINNET_DEPLOYED_ADDRESSES.md`.
2. Перевірте фіналізацію ролей — той самий `cast call`-патерн, що ми
   використовували на Sepolia:
   ```
   cast call <ShieldSBT_адреса> "hasRole(bytes32,address)(bool)" $(cast keccak "DAO_ROLE") $(cast wallet address --private-key $PRIVATE_KEY) --rpc-url $ARBITRUM_ONE_RPC_URL
   ```
   Має вивести `false` — деплоєр не тримає `DAO_ROLE`.
3. Перевірте верифікацію на https://arbiscan.io для кожного з 16
   контрактів (зелена галочка "Contract").
4. **Негайно ініціюйте першу DAO-пропозицію** (розділ 4
   `PROJECT_ARCHITECTURE.md`):
   - `humanityGate.acceptGovernor()`
   - `treasury.setTipJarRole(address(tipJar), true)`

   До виконання цих двох кроків: `HumanityGate` формально ще керується
   деплоєром (хоч і не може вже нічого зробити з рештою протоколу), а
   пул-частка донатів накопичується в escrow всередині `TipJar` замість
   `Treasury` (гроші не губляться, просто чекають).

## Частина 6 — Типові збої саме на mainnet (яких не було на Sepolia)

| Симптом | Причина | Що робити |
|---|---|---|
| Транзакція "застрягла" в `[Pending]` набагато довше, ніж на Sepolia | Mainnet має реальне навантаження мережі, черга на послідовника (sequencer) Arbitrum може бути довшою за тестнет | Не панікувати, не надсилати ту саму транзакцію повторно з новим nonce — це створить конфлікт. Чекати або звернутись до підтримки RPC-провайдера |
| `insufficient funds for gas` | Баланс деплоєра менший, ніж оцінка з Частини 2 (ціна газу зросла між симуляцією і реальним запуском) | Поповнити гаманець, повторити СИМУЛЯЦІЮ (Частина 2) ще раз для свіжої оцінки перед повторною спробою `--broadcast` |
| Верифікація на Arbiscan не спрацювала для одного з контрактів, хоча деплой пройшов | Etherscan API rate-limit або тимчасова недоступність | Безпечно повторити окремо: `forge verify-contract <адреса> <контракт> --chain arbitrum-one --etherscan-api-key $ETHERSCAN_API_KEY` — жодного ризику для вже задеплоєного контракту |
| `nonce too low` / `nonce too high` | Гаманець-деплоєр використовувався одночасно для чогось іншого (порушення п.8 Частини 0) | Дочекатись завершення інших транзакцій з цього гаманця, синхронізувати nonce, не форсувати |
